## Component justifications

### 1. API framework — KEEP FastAPI

FastAPI's overhead is not on our critical path: a single-text classify spends ~18 ms in ONNX inference (p95 [measured]) against single-digit-millisecond framework routing/validation costs, so Litestar's ~2x throughput advantage (its own benchmarks doc attributes it to msgspec vs Pydantic [source: litestar-org/litestar docs/benchmarks.rst]; Better Stack guides claim ~2x [source]) and Robyn's Rust-runtime stability under extreme load (246 RPS ceiling for FastAPI on one laptop test; Robyn stable at 10k users [source: blueshoe.io, 2025-06]) buy nothing we can demo: our judge-visible property is correctness and p95 latency of a *model-bound* endpoint on one machine. What matters for a hostile panel is the thing FastAPI has and the others don't: the largest ecosystem (84k+ GitHub stars vs Litestar ~5.9k [source]), a hiring pool of students who already know it, and auto-OpenAPI docs — losing `/docs` by going bare Starlette would visibly hurt the demo. Rewriting routes.py (402 LoC) to gain ~0 ms on the measured path is textbook churn. msgspec defer: it benchmarks ~3.2x faster than Pydantic v2 for type validation on Python 3.14 ([source: shanechang.com migration writeup, 2025-11]), but our payload schemas are tiny (PredictionOut, 239-LoC schemas.py) and Pydantic 2.13.5 is already load-bearing; adding a second serialization library for an unmeasured win risks the demo for zero user-visible change.

### 2. Task/queue/background jobs — ADOPT stdlib primitives, defer a broker

Every real queue candidate demands infrastructure we can't carry into a judged offline demo: arq/rq/dramatiq/celery/taskiq all require Redis or another broker ([source: fluid.quantmind.com comparison; 2026 dev.to decision guide — "Broker: Redis" for arq/rq; Celery Redis/RabbitMQ/SQS]); procrastinate requires PostgreSQL — a server we already rejected for ops weight; huey is the lightest but still wants a separate worker process and its defaults push Redis. Brokerless durability exists only in a DB-polled design (the outbox pattern that fastapi-patterns.com notes "beats all three" for transactional work). The actual problems to fix are (a) bulk ingest at 11 rows/s [measured] — that is per-row transaction overhead in SQLite, which batching inside one transaction fixes for free, no queue involved; and (b) explanation precompute — genuinely optional, lossy work, which is exactly the class FastAPI `BackgroundTasks` is documented for ("use when the honest answer to 'what if this never runs?' is 'nothing'" [source: fastapi-patterns.com]). BackgroundTasks' real limitation — no durability across a restart, no retries [source, same page] — is acceptable because ingest writes are already durable in SQLite and idempotent via `report_hashes`. For CPU-bound bulk ingest, run classify on a `ThreadPoolExecutor` so the event loop keeps serving reads (onnxruntime releases the GIL). If restart-survivable ingest jobs are ever needed, a ~50-LoC sqlite job table polled by one thread is the ceiling; anything broker-backed is rejected until a second machine exists.

### 3. Vector / near-dup / search — KEEP numpy, DEFER sqlite-vec

The numbers argue against every "database-shaped" replacement at our scale. sqlite-vec's own brute-force benchmark shows 67.84 ms per full-scan query for 100k×384-d float32 on an M1 Pro [source: asg017/sqlite-vec exhaustive-memory benchmark]; our numpy matvec path is ~19.7 ms extrapolated at 100k rows and 13.8 ms per /classify row today [measured] — numpy is ~3.4x faster than the extension's scan at our ceiling, and 100x better proven. sqlite-vss is abandoned by its author (Faiss integration issues, documented by Alex Garcia himself [source]) — reject outright. DuckDB's VSS and sqlite-vec both add an engine for a brute-force problem we already solved. hnswlib/vectorlite would introduce ANN + a new C++ dep to get *worse than exact* recall for a near-dup banner that must not false-positive in front of judges. The maintenance story kills any doubt: sqlite-vec is pre-v1 with documented breaking changes, went through a visible maintainer hiatus in 2025 ("This project hasn't been updated for half a year" issue #226; author: "weekends only"), returned in 2026 with ANN/DiskANN alphas, and sprouted a community fork (vlasky) — single-maintainer risk is real [source: github issues]. The custom code we'd delete is ~100 LoC of measured, threadpoolctl-pinned index code; the swap trades measured correctness for a version-fragile extension on the offline pendrive. Revisit only if the index passes ~1M rows or needs multi-process access.

### 4. Model serving — KEEP hand-rolled onnxruntime

Our artifact is not a transformers-standard task: it is a custom multi-task graph (sif_logit + 7 rule heads + span logits, training-ordered heads verified against train.py) with sliding-window max-pool chunking and a temperature calibration (T=1.648) applied in classifier.py — no ORTModel/optimum class abstracts any of that, so adopting optimum would give us a `forward()` wrapper we immediately override while it drags `transformers` + `huggingface_hub` into the runtime venv. That crosses a line the repo has already drawn: requirements-dev.txt deliberately keeps transformers out of runtime and DECISION_LOG D12 records optimum-onnx as rejected for export [measured]. ORT GenAI and serving layers (Triton et al.) assume docker/server orchestration — forbidden on the critical path. The documented best practice (load one `InferenceSession` in lifespan, pin `CPUExecutionProvider`, cache input names, tune `intra_op_num_threads`) is exactly what classifier.py already does [source: onnxruntime.ai docs; codezup/MLjourney 2025 guides], and the outcome is measured: p95 ~18 ms single-text CPU [measured]. The only worthwhile additions are zero-dep: assert the quantized graph actually loads with `quantize_dynamic` output (already done by onnx_classifier_check) and keep the mock-contract regression harness.

### 5. Database — KEEP SQLite, fix its defects; defer DuckDB

Re-evaluating honestly, Postgres+pgvector stays rejected: it converts "single demo machine, no docker" into a server process with a service unit, users, and a backup story — pure ops weight for zero capability we need, and the vector half is already covered by §3. DuckDB is the genuinely tempting one: columnar + vectorized aggregates are 10–100x faster than SQLite on GROUP BY/scan analytics ([source: posthog.com; toolbox365; datacamp 2025 comparisons]), it's MIT, pip-installable, single-file, and could make /density-with-time-filtering trivially fast. But our write pattern is the opposite of DuckDB's sweet spot: SQLite is 2x–500x faster on frequent small writes ([source: hakunamatatatech 2026; marending.dev measured ~30–40k inserts/s SQLite vs ~4k naive DuckDB]), our workload is OLTP (row inserts, 1:1 prediction upserts, append-only overrides), and a second engine doubles the failure surface on a pendrive install. DuckDB *can* read SQLite files via its sqlite extension — that hybrid (SQLite writes, DuckDB analytics reads) is the correct future migration if /density must handle millions of rows with time filters; at today's 4.5k rows and 21–103 ms full-scan [measured], the honest fix is the one we skipped: `PRAGMA busy_timeout`, secondary indexes on the facet columns, and batched ingest commits — zero new dependencies, and it removes the verified 5-second-block-then-500 defect class. Both fixes belong to storage.py, not to a new engine.

### 6. Observability/logging — ADOPT structlog + prometheus-client; REJECT OpenTelemetry

Nothing today means a 500 on a concurrent write shows up as… nothing. The minimum credible "production-shaped" story for a judged offline prototype is two small, no-server dependencies: structlog (JSON stdout logs with request_id/route/latency_ms, a tiny `py3-none-any` wheel — structlog 26.1.0 confirmed downloadable [measured]) and prometheus-client (one `/metrics` endpoint with RED metrics: request rate, error rate, duration histogram, plus app counters — flag rate, gate hits, near-dup hits, ingest rows/s; prometheus-client 0.26.0 `py3-none-any` confirmed [measured]). Route-pattern labels only (`/api/classify`, not per-URL) to keep cardinality bounded [source: standard practice, e.g. blueswen/telemify patterns]. OpenTelemetry is over-engineering here and I judge it as such: the Python OTel stack is SDK + per-framework instrumentors + an exporter aimed at a collector/backend (Tempo/Grafana/collectors in every reference stack [source: patex1987 POC repo]), which is exactly the multi-process docker-shaped infrastructure the demo forbids; its dependency weight on the vendored pendrive is pure risk with no judge-visible payoff. What OTel buys — cross-service correlation — is meaningless for a single process. Hand-rolled-only is the fallback (a dict-shaped log call is ~30 LoC), but structlog is small enough to be the more professional-looking answer on the same effort. Keep the existing hand-written `/api/metrics/summary`; it's the demo-friendly human view.

### 7. Configuration/settings — ADOPT pydantic-settings

config.py hand-rolls per-field env parsing (`int(os.environ.get(...))`, `float(...)`, a bespoke bool parser repeated per field — `"1".lower() not in ("0","false","no")`). That is exactly the custom code category we are told to delete, and it carries a real failure class: silent-wrong-value boot (cast-at-read-site accepts bad environments and `bool()`-style casts accept misspellings [source: fastapi-patterns.com — `bool("flase")` is `True`]); pydantic-settings validates the whole object at construction and reports every error at once [source, verified pattern]. pydantic 2.13.5 is already installed and running on 3.14, so pydantic-settings adds one small pure-Python package on the mental model the codebase already uses (schemas.py) — pydantic_settings 2.15.0 `py3-none-any` confirmed downloadable [measured]. Keep the frozen/immutability behavior (`model_config = SettingsConfigDict(frozen=True)`) and the same `SIF_*` env names so the pendrive selfcheck and README don't change. dynaconf is rejected: its layering/multi-format machinery solves a problem (many environments, many file formats, runtime reload) that a single-machine, env-var-driven demo does not have. Honest caveat: the current 83 LoC works today, so this is a low-value-but-low-risk adoption — do it opportunistically, not as a fire-drill.

### 8. Testing — ADOPT pytest structure + hypothesis on the gates; defer snapshot testing

Current assets: adversarial_suite.py (stdlib-runnable red-team script — keep it runnable; it doubles as the pendrive selfcheck), app/tests/*_check.py contract scripts, 5 Playwright e2e specs, pytest 9.1.1 installed [measured]. Gaps: nothing asserts *properties*, only 18 hand-picked cases. The gates are the perfect hypothesis target because their invariants are crisp: `text[start:end] == span.text` span validity (already a stated contract invariant in classifier.py), min_length never tripping a report that is only a short-code (SEV1 register #7), negation-window detection, language-ratio monotonicity, chunked_low_score ordering. Hypothesis generates the pathological inputs we didn't think of and shrinks them to minimal reproducers; cp314 wheel confirmed (hypothesis 6.168.1) [measured]. Two honest properties to start: "gates never crash on arbitrary text" (the free one) and "span validity holds for any PredictionOut the classifier emits". Snapshot testing (syrupy, zero-dep, MIT [source]) is deferred deliberately: our classifier is seeded by sha256(text), so deterministic regression tests already exist; snapshots of model outputs ossify bugs on retrain/re-calibrate (T=1.648 will change) and add amber-file churn a 4-person team will stop maintaining. The one place a snapshot earns its keep is the OpenAPI schema (stability of the API contract) — worth ~10 LoC if ever needed, not a milestone.

### 9. Rule-engine / NLP-pipeline libraries — prior rejection CONFIRMED with evidence

The earlier agent's rejection survives scrutiny. Evidence: durable-rules last PyPI release 2.0.28 shipped June 2020 — 5+ years stalled [source: pypi.org project page]; pyknow development "effectively stopped", experta is the community fork [source: nected.ai 2026 audit] under **LGPL-3.0** (a copyleft obligation the repo hasn't accepted) with no corporate cadence; python-rule-engine is a flat JSON condition matcher — and our gates are not flat conditions: gate_near_dup queries the embedding index, gate_negation is a windowed regex over ±token spans, gate_confidence compares a temperature-calibrated float. Expressing heterogeneous predicates as a declarative JSON/RETE fact model adds a second mental model (facts, salience, conflict resolution, RETE) to 10 stateless functions that currently read top-to-bottom in one file. Experta's own docs warn that one asserted fact can cascade into others — the exact debugging cost CLIPS users inherit [source: experta docs] — for zero lines saved: the 423 LoC includes regex tables, docstrings, and doc'd thresholds; the replaceable logic is a fraction of that. `business-rules` (the pypi.org package) is a declarative condition-tree DSL — same mismatch. If rules ever become judge-editable data (a possible demo feature), a **structured registry table** (name → function pointer + params) is the honest 30-LoC answer, not an engine.

### 10. Indic language handling — DEFER, with a designed hook; Hindi/Assamese prevalence is measured ~0

Measured reality first: 0 of 5,056 rows in runtime.db and 0 of 4,548 in demo_pre.db contain Devanagari codepoints [measured, read-only sqlite GLOB] — so translate-before-classify protects against a *future* corpus, not the demo corpus. That tips the verdict to defer, not adopt. If adopted, this is the only viable offline path, and it happens to fit our stack: **IndicTrans2** — MIT-licensed model checkpoints [source: AI4Bharat/IndicTrans2 GitHub], covers all 22 scheduled languages including Hindi (`hin_Deva`) and Assamese (`asm_Beng`), with models at 1B (en↔indic, indic↔indic) and distilled 200M (en↔indic) / 320M (indic↔indic) [source]. Two viable no-torch-at-runtime serving paths, both pip-offline-vendorable:

- **CTranslate2** (C++ runtime, Python bindings; int8 via oneDNN/MKL on x86-64 [source: CT2 docs/quantization.md]; int8 needs no calibration — weights-only with fp32 activations). AI4Bharat ships official CT2-ported checkpoints for inference [source]. Wheel for our interpreter confirmed: ctranslate2 4.8.2 cp314-cp314 manylinux_x86_64 downloads cleanly from PyPI [measured]; it contains no torch dependency. CT2 OPUS-MT reference: 696 tok/s int8 on a 4-thread c5.2xlarge [source: CT2 performance.md]; IndicTrans2 CT2 CPU tok/s on Ryzen AI 7 350: **unverified — not measured**. Sentence-level estimate: 200M distilled ≈ 0.3–1.5 s; 1B ≈ 1–4 s per report [estimated].
- **ONNX + our existing onnxruntime/tokenizers stack**: community INT8 exports exist (hari31416/indictrans2-onnx-export). INT8 bundle sizes: indic→en 1B = 1,020.1 MB; indic→en 200M = 335 MB; en→indic 200M = 335 MB (335 MB per that repo's int8 sibling) [source]. Quality warning from the same repo: INT8 token-match drops to 94.45% (1B indic→en) but only 85.64% (200M indic→en) — "the 200M/320M models can drop sharply; the 1B variants hold up much better" [source]; that repo's own 200M-int8 card says "research artifact — not for production" [source]. Latencies quoted there (10–31 ms batched) are on unspecified hardware, likely GPU — **unverified for our CPU** [unverified].
- **Preprocessing risk**: IndicProcessor/normalization (sentence-split, script sanity) comes from the IndicTransToolkit; whether its current version preprocesses without importing torch is **unverified** — the legacy `ai4bharat-transliteration` pip package pins `fairseq` (→ torch) [source: PyPI metadata], so IndicXlit is rejected for runtime on that basis alone, and the toolkit must be checked the same way before any adoption.

Sizes to vendor offline: ≥335 MB (200M int8) to ~1 GB (1B int8) of weights into artifacts/ — pendrive-sized but real; the CT2 4.8.2 cp314 wheel is confirmed pip-downloadable for our interpreter [measured]. **Indic Photo OCR v2** was not reachable in this research pass [source unreachable] — out of scope for text reports anyway; revisit only if photo evidence becomes a judged scenario. The cheap, zero-risk move now: keep gate_language exactly as is, add a `translate` hook beside explain.py's LLM pattern (deterministic path always ships, translation best-effort with timeout + fallback to gray-out), and record the decision. That preserves demo reliability and claims the feature credibly when Hindi/Assamese corpora actually appear.

## What modern tooling we should NOT adopt (and why)

- **OpenTelemetry SDK/instrumentors/exporters** — built for a collector/backend we can't run; over-engineering for a judged offline prototype (§6).
- **Any broker-backed task queue** (celery/dramatiq/rq/arq/taskiq/huey-worker) — all need Redis or a second process; our durability lives in SQLite already (§2).
- **DuckDB as primary DB** — wrong write profile, second engine on the demo machine; only as a future read-side analytics extension (§5).
- **sqlite-vss** — abandoned by its author (§3).
- **hnswlib/vectorlite/faiss** — ANN machinery for a brute-force problem numpy already solves faster at our scale (§3).
- **optimum / ORT GenAI / transformers at runtime** — violates the no-torch-adjacent-runtime design; DECISION_LOG D12 already rejected it for export (§4).
- **experta/pyknow/durable-rules/business-rules** — stalled maintenance, LGPL, second mental model for 10 stateless gates (§9).
- **IndicXlit at runtime** — pip package requires fairseq → torch; and transliteration ≠ translation (§10).
- **Syrupy snapshot tests** — ossifies calibrated model outputs that legitimately change on retrain (§8).
- **dynaconf** — layering machinery for a flat env-var surface (§7).
- **Robyn / bare Starlette / Litestar** — rewrite risk for zero judge-visible gain; ecosystem + /docs + student familiarity win (§1).

## Top-3 risks

1. **Offline vendoring of the three adopted wheels** — verified downloadable from PyPI today [measured], but the pendrive build must pin them into the wheel bundle and selfcheck must assert they import on a clean 3.14 venv; otherwise §6/§7 upgrades quietly regress to hand-rolled code.
2. **SQLite fixes are code changes, not adoption** — `busy_timeout` + batched commits + indexes touch storage.py's write path; the 11-rows/s ingest fix must be re-measured (target: >200 rows/s [estimated]) and the concurrent-write 500 must be re-tested under a held external lock before the fix is called done.
3. **IndicTrans2 preprocessing dependency chain is unverified** — if the judges demo Hindi input, the translate-before-classify path hinges on IndicTransToolkit preprocessing without torch and on CPU latency we never measured; until then the language gate's gray-out is the only honest behavior (0 Hindi rows in demo corpora [measured]).
